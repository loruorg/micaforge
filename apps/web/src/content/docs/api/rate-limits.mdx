Limits exist to bound a broken loop, not to police traffic. They are counted in fixed
windows in Valkey, keyed per site and per salted address digest: the limiter holds no
address either.

## Ingest

**600 hits per minute, per site, per address.** Deliberately generous: a documentation site
behind one corporate NAT is a legitimate source of hundreds of hits a minute, and
throttling it would delete real readers.

Over the limit, `POST /api/track` still answers `204 No Content` and the hit is dropped. A
tracker must never learn anything it could leak, and a page must never be told its
analytics failed: an accepted hit and a dropped one look identical from the browser, on
purpose.

**`POST /api/log/edge` is different.** It answers `429` with `Retry-After: 60`, because a
shipper being throttled needs to know and there is no page to protect. Both the shipper and
the server SDK back off and retry on a 429 without being told.

Two size limits sit alongside: 200 payloads per `/api/track/batch` call, and 500 rows per
array per `/api/log/edge` call, inside a 2 MB body.

## Authentication

| Endpoint | Limit |
| --- | --- |
| `POST /api/auth/code` | 10 per 10 minutes per client address, and 3 codes per 10 minutes per email address. |
| `POST /api/auth/code/verify` | 30 per 10 minutes per client address, and 10 per 10 minutes per email address. |
| `POST /api/auth/totp/disable` | 5 per 15 minutes per account. |

The email-address limits apply to every address alike, whether it has an account or not, so
a `429` from them reveals nothing. The one on asking for codes keeps the mail path from
being used to flood somebody's inbox. The one on verifying is the bound on guessing: it is
counted with an atomic increment before the code is even read, so neither parallel requests
nor requests from many client addresses get more than ten guesses per address per window.
Each code also dies after five wrong guesses.

## Reads

The analytics endpoints are not rate limited today. They are authenticated, they are bounded
by what a key can reach, and a self-hosted install is answering only to its own operator.

That is a statement about how it is built, not a promise to keep forever: if you are
building something that hammers the read API, build it to handle a `429` anyway.

## AI questions and feedback

| What | Limit |
| --- | --- |
| Questions to the [AI analyst](/docs/dashboard/ask-ai) | `MICAFORGE_LLM_DAILY_LIMIT` per organisation per UTC day, shared by the dashboard, the MCP `ask` tool, the chat apps and investigation explanations. `0`, the default, is no limit. |
| [Feedback](/docs/api/feedback) reports | 20 per hour per reporter. |

Both answer `429 rate_limited`, and the AI limit sends `Retry-After` with it. A question
costs a call to a model the operator pays for or runs, which is why it has a budget when the
reads have none.

## What a limited response looks like

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

```json
{ "error": { "code": "rate_limited", "message": "too many edge batches for this site" } }
```

Branch on `error.code`, honour `Retry-After`, and back off exponentially with jitter after
that. Both shipped clients do.

## Staying under them without trying

- **Batch instead of looping.** One call with fifty rows, not fifty calls.
- **Let the SDK hold the queue.** The server SDK sends on a 200 ms window or at 50 queued
  hits, whichever comes first. Nothing is awaited on your request path.
- **Cache reads that feed a dashboard.** A page refreshing an overview every second is
  asking one question 60 times a minute, and the answer changes on the minute at best.
- **Export instead of paging.** A whole table is one `export.csv`, not two hundred pages.
